### Judgments requested
- `Rescan_OfT_LeavesUsPumpRunning` (RescanTests, third test): it does prove U applies while T's producer is held. `producing.Entered` is awaited first, so T is inside its held production; then U's `Publish` is awaited (and the pump-side apply result is observable: U's `UsnNextUsn == 555`, a `Changed` entry "u.txt"), with `rescan.IsCompleted == false` asserted after and `otherHandle.DisposeCount == 0`. Failing-first evidence: on this base `ApplyJournalEntriesCore` takes the index-wide `_swapGate` (FileIndex.Watch.cs:98) while the rescan takes it only at the swap (FileIndex.Rescan.cs:221), so the implementer's substitute (test holds `_swapGate` after production entry, U's publish then times out) reproduces exactly the regression "an index-wide gate held across production". That shows the test can go red for that regression, but it is a test-side mutation, not a production mutation, so it does not show that a regression in `RescanWithGatesHeldAsync` (for example retiring other drives, or holding another drive's write gate once B5 lands) would be caught. It would: those paths would hang U's `Publish` or dispose U's handle, both covered by the assertions. Acceptable; a production-side scratch mutation remains undone because the classifier denied it, which the report discloses. Recommend the controller accept it, optionally running the retire-other-drives mutation once.
- Concern 1 (failed restart after a replaced faulted drive loses the old fault): spec 2.6.4 says a rescan "retire[s] Current" then restarts through the start helper, that start "retires a Faulted current instance", and that a start failure "records X's failure message, faults the instance's slot, clears Current, completes Drained and propagates". Stop "takes the instance's outstanding fault" from the instance it retires, so with `Current` cleared there is nothing left to rethrow; the rescan itself throws the restart failure to its caller. So the code follows the letter of the spec, and the port is not a B1 production defect. It is a spec gap: the base contract ("previously outstanding fault survives a failed re-arm") is neither preserved nor explicitly revoked, and the spec does not say whether stop after a failed restart throws `InvalidOperationException` (no instance) or returns quietly (`WatchRequested` set). Recommendation: the controller decides and pins it in the spec; then the port should assert it (see Important 1). Not blocking B3 on its own.
- Concern 2 (fault during production recast): valid. Spec 2.6.4 has rescan retire `Current` and await `Drained` before production, and 2.6.2 says a retiring pump's faults are not recorded, so "a fault recorded while the producer runs" cannot arise. The recast pins the reachable equivalent (accepted batch fails during the drain: no fault, no checkpoint check, healthy restart from the old cursor after failed production) and its gating is sound (`Assert.IsFalse(rescan.IsCompleted)` while the apply is parked, faults counted after the rescan returns, i.e. after `Drained`). One caveat: the dropped apply failure means the batch is lost silently by design; the old cursor is retained so it is re-read after restart, which is what `starts[1] == (JournalId, NextUsn)` asserts.
- Concern 3 (all-drives catch-up test dropped): acceptable; the no-list form does not exist until B7. Ensure B7's brief lists the dropped method by name.
- Weakening summary: beyond Important 1, the removed `WatchFaulted(Source)` announcement assertions and the changed `WatchFailureMessage` in the two restart-failure tests follow the contract change (no source-kind fault, failed start records its own message). `CheckpointLoss`, `HealthyDrive`, `SuccessfulRetry` and `CancelledPublication` retain every substantive base assertion (the last gains nothing lost; the `ended` parameter is gone with sessions).
