### Issues

#### Important (Should Fix)

1. **`BlockFile.Open` deletes reachable file-system failure handling and breaks cache fallback.** The removed `try` covered `new FileInfo(path)`, `Exists`, and `Length` (base `BlockFile.cs:238-248`); current code at `BlockFile.cs:225-232` has no handler until after those operations. The official [.NET `FileInfo` constructor documentation](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileinfo.-ctor?view=net-10.0) names `UnauthorizedAccessException`, `PathTooLongException` (an `IOException`), `SecurityException`, `ArgumentException`, and `NotSupportedException`; the old catches handled the first two categories. [`FileInfo.Exists`](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileinfo.exists?view=netframework-4.8.1) returns false when its refresh fails and caches a successful refresh, but that does not make constructor failures impossible. [`FileInfo.Length`](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileinfo.length?view=net-10.0) documents `IOException` and `FileNotFoundException`, both handled by the deleted `IOException` catch. The later `OpenMapped` handlers at `BlockFile.cs:283-320` still correctly cover `IOException` and `UnauthorizedAccessException` from the `FileStream` at `BlockFile.Mapping.cs:20-21` and the view at lines 25-27. The official [`FileStream` constructor](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.-ctor?view=net-10.0), [`MemoryMappedFile.CreateFromFile`](https://learn.microsoft.com/en-us/dotnet/api/system.io.memorymappedfiles.memorymappedfile.createfromfile?view=net-10.0), and [`CreateViewAccessor`](https://learn.microsoft.com/en-us/dotnet/api/system.io.memorymappedfiles.memorymappedfile.createviewaccessor?view=net-10.0) document the expected I/O, access, file-not-found/directory-not-found/path-too-long, and argument failures. Those mapping failures never reached the deleted outer handler because `OpenMapped` was already called after it. The regression is specifically the pre-mapping `FileInfo` failures: they now bubble through `TryOpenExistingBlock` and `Task.WhenAll` (`FileIndex.Scanning.cs:13-35,101-104,341-377`) and make `OpenAsync` fail. This contradicts `BlockFile.Open`'s own unreadable-file contract at `BlockFile.cs:210-216` and `docs/index-format.md:3-7`, which says a normal open rejects an unusable cache and rescans. Restore the reachable handling and test it through an injectable instance-level file-metadata seam.

2. **The blockless-status invariant throw is reachable and was only moved out of coverage.** `OpenCoreAsync` invokes arbitrary internal callback code on the new index before settling at `FileIndex.cs:157-169`. A non-elevated test can call `opening.Drives` there. `Drives` sees a configured drive at `FileIndex.cs:121-125`, while both `_driveBlocks` and `_blocklessDriveStatuses` are still empty, so the old custom throw was reachable. Current `DescribeBlocklessDrive` at `FileIndex.cs:379-382` still throws for the same condition, but through `Enumerable.First`; the guard was not dead, only relocated to framework code. This fails the owner ruling that every reachable MFTLib.Index line gets a behavioral test and only a guard that can never execute is deleted. Either prevent the seam from exposing an unsettled `FileIndex`, or retain and test the invariant behavior.

3. **Three new seams violate the instance-level, non-static requirement.** `FileIndex.OpenCoreAsync` is explicitly called a test seam and declared static at `FileIndex.cs:152-158`. The guard-state overloads are also static at `CacheDirectory.cs:36` and `JournalCheckpointCheck.cs:118`; the implementer's report itself lists them as seams. Pure arguments and lack of new global state make them safer than mutable static hooks, but they still do not satisfy the task's explicit shape. `OpenCoreAsync` also gives callback code a half-open index and adds a null callback branch to every public open at `FileIndex.cs:148-166`. Replace these with instance-owned dependencies or another internal instance construction path that cannot expose an unsettled public object.

4. **New async tests violate the bounded-await rule.** `OpenAsync_CacheMode_RetiredSiblingListingFails_OpensAndLeavesTheSibling` awaits `File.WriteAllTextAsync` without a token or timeout at `FileIndexResilienceTests.RetiredSiblings.cs:87`, then awaits `OpenCoreAsync` with `CancellationToken.None` and no `WaitAsync` at lines 90-99; its implicit async disposal is unbounded too. `StopAfterTheRescanDecidedToRestart_StopWins` awaits the initial start without `WaitAsync` at `FileIndexWatchRecoveryTests.RestartDecision.cs:19` and awaits `Assert.ThrowsExceptionAsync` without an outer bound at lines 42-43. The same test correctly bounds rescan and stop at lines 35 and 38, so the missing bounds are straightforward to fix. No test added by this diff uses a real-time delay or elapsed-time assertion.
