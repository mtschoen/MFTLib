### Issues
#### Critical (Must Fix)

#### Important (Should Fix)
- `MFTLib/Index/BlockFile.cs:287-291`: Windows now throws immediately for any failed `FlushViewOfFile`. The net10.0 implementation retries only `ERROR_LOCK_VIOLATION` (33): after the initial failure it performs up to 15 increasing sleep stages, each with 20 retries and spin waits, while any different error still throws immediately ([runtime source, lines 107-139](https://github.com/dotnet/runtime/blob/release/10.0/src/libraries/System.IO.MemoryMappedFiles/src/System/IO/MemoryMappedFiles/MemoryMappedView.Windows.cs#L107-L139)). Dropping that loop can turn a transient failure that the old `MemoryMappedViewAccessor.Flush()` would recover from into a `Win32Exception`. This violates `BlockWriter.Complete` keeping its current behavior and makes large ranged flushes more fragile because each range is another opportunity for this known NTFS error. Carry the runtime's bounded retry semantics into each Windows range.
- `MFTLib/Internal/Libc.cs:9` and `MFTLib/Index/BlockFile.cs:285-299`: the direct libc flag is not portable across the branch it guards. Linux defines `MS_SYNC` as 4, but Darwin defines `MS_SYNC` as `0x0010` and 4 as `MS_KILLPAGES` ([Linux header](https://github.com/torvalds/linux/blob/master/include/uapi/asm-generic/mman-common.h), [Darwin header](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/mman.h)). Since the implementation chooses this path for every OS other than Windows, a macOS call does not request the required synchronous flush and can return without the durability callback actually representing an `MS_SYNC` completion. Use platform-correct native flags or a portable platform interop layer; alternatively, make the supported-OS restriction explicit and enforce it before the P/Invoke rather than silently using Linux constants elsewhere.
- `.superpowers/sdd/2026-09-28-per-drive-watch-channels/task-W40-report.md:20`: the implementer explicitly did not run the new tests red before implementation. Both the task brief and global constraints require writing the named tests, observing each fail for its stated reason, and only then implementing (`.superpowers/sdd/2026-09-28-per-drive-watch-channels/task-W40-brief.md:49`, `.superpowers/sdd/2026-09-28-per-drive-watch-channels/global-constraints.md:69`). A later caller compilation failure is not evidence that each new behavioral test failed for the intended reason. This is an explicit task-gate miss even though the resulting tests are substantive.
