# Changelog

## 0.3.0

- Add `MftIndexSources.FromMftDumpFile(filePath, driveLetter)`: an index source that loads a saved `$MFT` file as one virtual drive, in process, with no broker and no elevation, on Windows and Linux. Open it with one drive `new IndexedDrive(letter, "dump:/" + letter, 0)`, `NoCache` and `ProducerPolicy.Mft`. A dump is untrusted: an empty file, a record size other than 1024 or 4096, a partial final record, an invalid fixup on an allocated record, a file that cannot be read to its opened length, a missing or invalid root, duplicate record numbers or a parent outside the index each fail the scan with its own message in `DriveStatus.FailureMessage`.
- The native parser validates a record's update sequence array before using it. A record whose fixup is invalid is never decoded: a file parse fails on an allocated one, a volume scan passes over it, and a volume scan whose bootstrap record (record zero) has an invalid fixup fails before any attribute is read. `MftDumpInput` rejects an empty file (`The dump file is empty.`) instead of returning no records, and reports a failed or short read instead of returning the records read so far.
- Add `BrokerSession`, the one public type that owns a consumer session's elevated broker: it launches the process on first use (`new BrokerSession()`), reports `Connecting` and `Connected`, exposes `HasEnded` and `Ended` (a sticky end with the reason; every later use throws `InvalidOperationException` naming it, and it never relaunches), hands out `CreateIndexSource(scanOptions)` and `GrowUsnJournalAsync`, and disposes the process. One shared launch that no single caller's cancellation can abort; a failed launch (the UAC prompt declined, a connect timeout) is not cached, so the next use launches and prompts again; disposal cancels and awaits an in-flight launch and reclaims a late process. Both file-wizard and git-wizard delegate session ownership to it. `MFTLib.TestExtensions` adds `BrokerTestHarness.CreateSession(launchAsync)` so a test hands a session the broker of an in-process handle. See `docs/broker-integration.md` section 2.
- Add the Benchmark `index` scenario for synthetic or cache-only blocks, reporting per-drive block geometry, name-pool share, and median warm exact and substring `Search` latency.
- The MFTLib package carries `runtimes/linux-x64/native/libMFTLibNative.so`, the Release library built on Ubuntu 24.04, so a package user on Linux can load an MFT dump with `MftIndexSources.FromMftDumpFile`; it requires glibc 2.33 and GLIBCXX_3.4.22. `scripts/release.ps1` builds it in WSL, `scripts/Test-ReleasePackages.ps1` requires the entry, and the `linux-package` CI job packs and runs a consumer project against it (`docs/linux-package.md`).
- Native ABI 7: the parser no longer filters names or resolves paths. Deleted: the native name filter, path table and resolve pass, the `ParseMFTFromFile`, `ParseMFTFromFileUtf8` and `ParseMFTFromFileUtf8WithProgress` exports, the UTF-16 generator exports, `MatchFlags`, `MftScanPhase`, `MftScanProgress.Phase`, the progress callback's phase argument, the path fields of the native result, and the internal `MftVolume.StreamMftFromFile`, `MftRecord.FullPath` and `MftRecord.ToString`. `ParseMFTRecordsWithProgress` takes `includeFreed` in place of the filter and flags, the UTF-8 generators are exported on every platform, and a saved image parses only through `MftDumpInput`, which never returns freed records. No public member changes.

### Public API cleanup

- `PublicMemberCallerTests` now proves every public member of `MFTLib` and `MFTLib.Index` has a sample caller or a reasoned consumer production caller, by reading the compiled IL of both samples. Record members are excluded as synthesized only on metadata evidence (`CompilerGeneratedAttribute`, and for the primary constructor an exact name and type match with the synthesized `Deconstruct`); every authored record member and every record property needs a caller. A record's automatic property is called by a sample reference to an accessor, or to a public constructor whose own straight-line IL (no branch, no `starg`, one `stfld`) stores an argument straight into its backing field; delegating-only, setter, constant, branching, overwriting and non-public constructors credit nothing, and only types carrying the compiler-marked `op_Equality` are records. A `constrained.` call of `ToString`, `Equals(object)` or `GetHashCode` declared on `System.Object` references the true override of the constrained library type (a closed generic resolves to its definition; hiding methods, interface callees, type parameters, boxed and nullable receivers and interpolation credit nothing). The `CompilerGeneratedAttribute` is matched by full name. The gate fails when two public members share a key. Exempt reasons are stated by people and not verified against consumer IL. `FileIndex.RescanAsync(CancellationToken)` is deleted and four overloads no one calls are internal: `StartWatchingAsync(IReadOnlyList<char>, CancellationToken)`, `StopWatchingAsync(char, CancellationToken)`, `StopWatchingAsync(IReadOnlyList<char>, CancellationToken)` and `WaitForCatchUpAsync(IReadOnlyList<char>, CancellationToken)`. Both samples print the drive of each scan phase, and the directory when the producer reports one; the Direct `open` verb names the entry it cannot open.
- `TestProgram` is now two samples that between them call the public API: `SampleProgram.Direct` (`search`, `tree`, `open`, `largest`, `duplicate-names` and `scan`, over a live volume or a saved MFT dump, on Windows and Linux) and `SampleProgram.Watch` (`scan-drive`, `watch`, `rescan`, `journal`, `cache` and `elevation-status` over the broker). The elevation notice, unattended check and elevation flow compile into both from `SampleProgram.Shared`. `MFTLIB_TESTPROGRAM_UNATTENDED` is `MFTLIB_SAMPLE_UNATTENDED`. No library change.
- Broker production plumbing is internal. Production callers use `BrokerSession.CreateIndexSource` and `BrokerSession.GrowUsnJournalAsync`. SampleProgram.Watch `scan-drive` owns one lazy session for the run and disposes it after its indexes.
- Remove legacy progress constructors and explicit deconstruction overloads. Use phase-bearing `MftScanProgress` construction, `BrokerScanProgress` property initialization, and the current `BlockWriteProgress` shape.
- Keep broker wire types, snapshot and mutation machinery, matching and file-open helpers, capacity planning, row writing, shared-memory implementations, and synthetic MFT generators internal. `MftPathUtilities` lives in test support; `ElevationUtilities.GetProcessPath` is internal.
- The watch and producer seams are internal: `IIndexWatchSource`, `IIndexDriveWatch`, `IndexWatchTarget`, `WatchStreamItem`, `DriveCaughtUp`, `JournalBatch`, `DriveWatchFaultException`, `MftBlockProducer`, `MftBlockProduceRequest`, `MftBlockProduceResult`, `EnumerationProducer`, `EnumerationProducerOptions`, `EnumerationResult`, `UsnJournalEntryOptions` and the `MftIndexSource` constructor. Only MFTLib implements them; consumers obtain a source from `BrokerSession.CreateIndexSource()` or `MftIndexSource.Unavailable(reason)`, and tests script one through `MFTLibTestExtensions`. `UsnJournalEntryOptions` also leaves the `MFTLib.Index` namespace-boundary allowlist.
- The block format types are internal: `BlockFile`, `BlockFileCreateOptions`, `BlockWriter`, `RowColumns`, `RowFlags`, `FileRow`, `NamePool`, `BlockFlags`, `BlockHeader` and `BlockLayout`. Only MFTLib writes blocks; the file format stays documented in `docs/index-format.md` for anyone reading a cache file, and tests write blocks through `MFTLibTestExtensions`. So are `CacheDirectory.BlockFileName`, both `CacheDirectory.EnumerateCached` overloads, the four-argument `CacheDirectory.DeleteCached` and `FileIndex.CacheDirectoryPath`. Cache inventory goes through `CacheDirectory.InspectCached`; `CacheDirectory.DeleteCached(path, driveLetters, diagnostics)` stays the lock-safe clearing API.
- Remove `DriveState.Scanning`, `MftBlockProduceResult.CompactionNeeded`, and the raw-volume `FindDirectories`, `FindFiles`, and `FindRecords` wrappers. Compaction status comes from the block header.
- `WatchUsnJournal` yields `(Entries, Cursor)` batches. Remove `WatchUsnJournalWithCursor`. Consumer tests inject journal batches through `MFTLibTestExtensions.FileIndexTestAccess.ApplyJournalEntries`; the production entry point is internal.
- `MFTLib.TestExtensions` adds `SyntheticBlock`, `SyntheticBlockEditor`, `SyntheticBlockOptions`, `SyntheticRow` and `SyntheticMftProducer`. They write and edit cache blocks and produce MFT blocks through the production block writer, with capacity planned from the rows. `SyntheticBlock.Edit` and `WriteCached` refuse a slot an open index owns. `SyntheticMftProducer` supplies a before-produce hook and a catch-up loss.
- The MFTLib package ships `lib/net10.0/MFTLib.xml`, and the build warns on any public member without documentation, so IntelliSense documents the whole public surface. `scripts/Test-ReleasePackages.ps1` asserts the file is present.
- Status and report records carry only fields a consumer reads. `JournalCatchUpLostException` reports `RecoveryStopped` and a message; drive and loss details are on `DriveStatus`. `JournalCheckpointLoss` carries derived loss sizes, while its journal positions are internal. `CacheTag` is constructed and compared whole, with internal component accessors. `MFTLib.TestExtensions` adds `SyntheticIndexInspection.ReadHeader` (producer, row count, cache tag and scan timestamp as a `SyntheticDriveHeader`), `SyntheticCheckpointLoss.WithJournalPositions` and `SyntheticCacheTag`.
- `MFTLib.TestExtensions` adds `ScriptedBrokerVolumes`, `ScriptedScan`, `InProcessBrokerScan`, `InProcessBrokerHandle.Scans`, `SyntheticIndexSource`, `BrokerDiagnosticsIsolation.FlushAsync` and `BrokerDiagnosticsIsolation.Log`. `BrokerTestHarness.StartInProcess(ScriptedBrokerVolumes)` is the only public start: a test scripts the volumes a real in-process host serves, the client creates real block sections and each scan's records go through the production row writer and filter. The four `StartInProcess(JournalBrokerHost, ...)` overloads and `BrokerTestHarnessOptions` leave the public surface. `SyntheticIndexSource.Create(producer, watches)` returns the `MftIndexSource` a test index takes.
- The samples show a system-modal heads-up dialog (with a beep) before self-elevation or an attended, unelevated broker launch, so the UAC prompt is expected and a stray key press cannot dismiss it unseen; a dismissal within 0.75 seconds is treated as accidental and the dialog is shown again, and an unanswered dialog times out as Cancel after five minutes. `MFTLIB_SAMPLE_UNATTENDED=1` makes the samples skip the dialog and every elevation request (`docs/elevation.md`).
- `MFTLib.TestExtensions` closes the gaps both consumers worked around: `ScriptedWatchSource.WaitForStartAsync(drive, startNumber, token)` is race-free (a watch already handed out satisfies it; `startNumber` counts the drive's watches from one), `SyntheticRow.IsFree` seeds a slot holding no record, `SyntheticBlockEditor.SetProducerKind`, `MarkSizeUnknown` and `MarkSizesUnknown` edit the header kind and row sizes in place, and `SyntheticDriveHeader.CompletedUtc` exposes the stored scan timestamp so `Complete` can write it back.
- `MFTLib.TestExtensions` adds `SyntheticBlockEditor.SetCacheTag(CacheTag)` to replace a cached block's consumer identity in place while preserving its scan timestamp, journal cursor, remaining header fields and rows, so tests no longer read, delete and rewrite a block just to give it a foreign tag.
- `DriveStatus` groups its block and watch values: `DriveStatus.Block` (a `DriveBlockStatus`: `Source`, `CacheSlot`, `LiveRowCount`, `ScanTimestamp`, `CompactionNeeded`, `SkippedRecordCount`, `AccessDeniedSubtreeCount`) and `DriveStatus.Watch` (a `DriveWatchStatus`: `Supported`, `Requested`, `CatchUpState`, `StateVersion`, `FailureMessage`, `ConsecutiveLostCatchUps`, `CheckpointLoss`), both never null; `MftProducerFailureMessage` is `DriveStatus.FailureMessage`. `JournalCheckpointLoss.AllocationDelta` and `MaximumSize` are `JournalCheckpointLoss.JournalSettings` (a `UsnJournalSettings`). `SyntheticNotifications.CreateJournalCheckpointLoss` takes a `UsnJournalSettings` in place of the last two parameters, and `FileIndexTestAccess.ApplyJournalEntries` takes a `SyntheticJournalCursor` in place of the journal identifier and next USN. Consumer migration: read `status.Block.*` and `status.Watch.*` where the flat members were read.
- Separate `DriveBlockStatus.SkippedRecordCount` for MFT omissions from `AccessDeniedSubtreeCount` for enumeration subtrees that could not be entered.
- The broker host and its plumbing are internal: `JournalBrokerHost`, its eight source delegates (`UsnJournalCursorQuery`, `MftRecordBatchSource`, `UsnJournalCatchUpSource`, `JournalBatchSource`, `NtfsVolumeInformationQuery`, `GrowUsnJournalQuery`, `BrokerBlockSectionFactory`, `BrokerChannelConnector`), `IBlockSectionWriter`, `BlockWriteResult`, `BlockWriteReporting`, `BlockWriteProgress`, `IBrokerOperationReporter`, `MftBlockRowFilter`, `BlockScanTarget`, `BlockScanOutcome`, `BrokerDriveScanResult`, `BrokerScanProgress`, `BrokerScanPhase`, `IElevatedEntryRunner` and `DefaultElevatedEntryRunner`. So are the broker client's per-drive scan, volume-query and connection-timeout members, `BrokerScanOptions.Progress`, the construction of the broker's channel-lost exception, and `BrokerDiagnostics.Log` and `FlushAsync`. `ElevatedEntryPoint.TryHandle(string[] arguments)` is the one entry point; it runs the production runner. TestProgram `scan-drive` opens a `NoCache` `FileIndex` over `BrokerSession.CreateIndexSource()` and prints the drive status, and its journal listing prints a per-entry status word. Tests reach the internals through `MFTLibTestExtensions`.
- Broker scan frames carry only the data needed by the client. A completed scan holds the cursor where catch-up finished; catch-up entries stay on the host and are delivered by a watch. The ready frame holds the skipped record count; row count and name-pool size are read from the block header. Volume information holds record size and valid length, and catch-up loss holds journal facts. The frame length limit is 16 MiB, enforced on write and read: a keep list that cannot fit fails with `ArgumentException`, an oversized watch batch fails that watch, and error and stalled text is cut to 32,768 units.
- Public names say what they hold: `FileEntry.Id`, `Modified` and `SizeKnown` are `RecordKey`, `LastWriteTime` and `IsSizeKnown`; `DriveWatchState.State` and `Version` are `CatchUpState` and `StateVersion`; `DriveStatus.WatchCatchUp` is `DriveWatchStatus.CatchUpState`; `IndexDriveOpened.SettledCount` and `Total` are `SettledDriveCount` and `TotalDriveCount`; `CachedBlockFile.LastWriteTimeUtc` is `LastWriteTime` (still UTC); `ScriptedDriveWatch.QueueBatch` is `QueueBatchAsync`. Parameters `brokerArgs`, `args`, `fourCc`, `nativePath` and `drive` are `brokerArguments`, `arguments`, `fourCharacterCode`, `path` and `driveLetter`.

### Migrating from 0.2

Plain migration work for a consumer moving from `0.2.0`, or from a 0.3.0 preview built before the per-drive watch channels change, to this release. Consumers are file-wizard and git-wizard; each item is the call shape to edit.

- Target net10.0 and compile against the `0.3.0` assemblies. Managed and native binaries must match (native ABI version 7), and every call site is recompiled because optional parameters were added to public methods.
- `volume.StreamRecords(filter, matchFlags)`, `ReadAllRecords`, `FindByName`, `ParseMFTFromFile` and `StreamMFTFromFile` -> an index source: `BrokerSession.CreateIndexSource()` or `MftIndexSources.FromLocalVolumes(scanOptions)` for a live volume and `MftIndexSources.FromMftDumpFile(filePath, driveLetter)` for a saved `$MFT` file, then look names up on the `FileIndex`. Neither source filters names; `FileEntry` carries the path. See the direct-API bullets below.
- `BrokerTestHarness.StartInProcess(...)` returns an `InProcessBrokerHandle` exposing `Ended`, `Crash()`, `Scans` and `DisposeAsync`; sessions use `CreateSession(launchAsync)`. file-wizard `FileWizardTests/TestSupport/BrokerProcessFixture.cs`: script scans with `StartInProcess(new ScriptedBrokerVolumes { ... })` and observe the handle. file-wizard `FileWizardTests/CliProgramCoverageTests.cs`: await `BrokerDiagnosticsIsolation.FlushAsync(...)` and reset through `BrokerDiagnosticsIsolation.Reset()`. git-wizard `GitWizardTests/TestSupport/BlockBrokerFixture.cs`: simulate broker death with `handle.Crash()`.
- `block.Flush()` -> `block.Flush(rangeFlushed: null)`; `writer.Complete(timestamp)` -> `writer.Complete(timestamp, null)`.
- Remove any caller of `BrokerDiagnostics.Log`, `FlushAsync` and `LogFrame`; they are internal. Consumer tests use `BrokerDiagnosticsIsolation.Log` and `FlushAsync`.
- Replace `JournalBrokerClient`, `JournalBrokerScanSession`, `BrokerScanResult`, and `NtfsVolumeQueryResult` with a session owned through `BrokerSession`; scans go through `session.CreateIndexSource()` and journal growth through `session.GrowUsnJournalAsync(...)`. Replace `ScanSessionTestHarness` with `BrokerTestHarness.StartInProcess` and create test sessions with `BrokerTestHarness.CreateSession`.
- Drop `--once` from broker launch code; the elevated child serves one control pipe, started by `ElevatedEntryPoint.TryHandle(args)`.
- Custom watch sources and block producers cannot be written outside MFTLib: take `BrokerSession.CreateIndexSource()` for production or `MftIndexSource.Unavailable(reason)`, and script tests with `ScriptedWatchSource`, `SyntheticMftProducer` and `SyntheticIndexSource`.
- `await index.StartWatchingAsync(token)`, `StopWatchingAsync(token)`, and `WaitForCatchUpAsync(token)` return one `DriveOperationResult` per configured drive; read each result's failure. Public single-drive calls are `StartWatchingAsync(char driveLetter, token)`, `WaitForCatchUpAsync(char driveLetter, token)` and `RescanAsync(char driveLetter, token)`. `RescanAsync(driveLetters, token)` returns one result per listed drive; stop uses the token-only all-drive call.
- `WatchFault.DriveLetter` is a `char`, not `char?`; replace `WatchFaultKind.Source` handling with `Drive`, `Channel`, `CatchUpLost`, `Recovery`, and `RescanRestart`. `IndexDriveOpened.Ordinal` is `SettledCount`.
- Scan progress: count a drive finished on `IndexScanPhase.Finished` (one per drive scan, with `IndexScanProgress.Outcome`), not on its first `Transferring` sample; enumeration-backed drives now report it too.
- Code that constructs `FileChange` passes the new `Timestamp`; code that constructs `IndexScanProgress` passes `DriveLetter`, `Phase`, and `RowsWritten`; `ProducerPolicy` has only `Mft` and `Enumeration`. Delete uses of the removed types listed under Removed.
- A drive whose watch start was refused over an unresumable journal cursor now reports `DriveWatchStatus.Requested == true`, and the rescan the refusal asks for restarts it. file-wizard `FileWizardMaui/MainPage.DriveRescan.cs` (`StartRescannedDriveWatchAsync`): key on `Watch.Supported && !Watch.Requested` instead of `WatchCatchUp == NotStarted`.
- Replace polling `Drives` for watch state with `FileIndex.WatchStateChanged`, applying an event only when its `StateVersion` is newer than the last one applied for its drive and seeding that from `DriveWatchStatus.StateVersion`. git-wizard's watch-state handling deletes its 500 ms recovery poll, `RecoveryPollInterval`, its `TimeProvider` seam and fault-generation map, and the double re-read in `TryFinishCaughtUp`, publishing `CaughtUp` from the recovered drive's `CaughtUp` event with that event's version; file-wizard `FileWizardMaui/MainPage.LiveUpdates.cs` reconciles drive health from the event instead of its 250 ms timer.

- Targets net10.0; net8.0 consumers must upgrade.
- Consumer tests supply journal records with `SyntheticJournalRecord` object initializers.

- Direct API, inside MFTLib: the volume batch read `MftVolume.ReadRecordBatches(batchSize, progress, parseThreads, cancellationToken, options)` (over `StreamRecords(includeFreed, progress, parseThreads, cancellationToken)`) and the dump parse `MftDumpInput.Open(filePath)` then `Parse(options)` are the only scan entry points; both are internal and back the index sources above. The eight array-returning overloads (`ReadAllRecords` x4, `FindByName` x2, `ParseMFTFromFile` x2) -> an entry point, then `MftResult.ToArray()`, `Timings` and `TotalRecords`. `MftVolume.DefaultBufferSizeRecords` (262144) names the default buffer size used by `Open`. Neither entry point filters names or resolves paths.
- `MftVolume.StreamMFTFromFile(path, filter, matchFlags, bufferSizeRecords)` -> `MftIndexSources.FromMftDumpFile(filePath, driveLetter)` for a consumer; inside MFTLib a saved image parses through `MftDumpInput.Open(filePath)` then `Parse(options)`. Execution controls (progress reporting, thread allowance, chunk buffer size, and cancellation) are grouped into `MftFileScanOptions`. The dump parse has the same progress, thread allowance and cancellation behaviour as `StreamRecords`, and both share one managed control-block path and one native core. Native ABI 7: `ParseMftDumpInput` and `ParseMFTRecordsWithProgress` take the `MftParseControl` block on every platform.
- `MftParseTimings` reports only native phases, as `TimeSpan` properties `NativeIo`, `NativeFixup`, `NativeParse` and `NativeTotal`, identical for every result. `MarshalMs`, `TotalRecords` and the `Ms` doubles are gone; read `MftResult.TotalRecords`, and time your own `ToArray()` for marshal cost.
- `MftVolume.QueryUsnJournal()` -> `MftVolume.QueryUsnJournalCursor()`, which says what it returns. `UsnJournalEntry.Timestamp` and `UsnJournalEntryOptions.Timestamp` -> `TimestampUtc`.
- `UsnJournalSettings` moves from `MFTLib.Index` to `MFTLib`, beside the other USN value types; `MftVolume.QueryUsnJournalSettings` and `GrowUsnJournal` no longer need `using MFTLib.Index;`. `MFTLib.Index` may reference it (the index reports it but does not own it).
- `MftVolume.Open` and `NtfsVolumeInformation.Query` name their parameter `volumePath` and document the same formats: a drive letter, a raw device path or a volume GUID path.
- `ElevationUtilities.IsElevated()`, `CanSelfElevate()` and `TryRunElevated(string arguments, int timeoutMs = 60000)` are no longer public; `IElevationProvider`, reached through `ElevationUtilities.DefaultProvider`, is the one way to run them, and `TryRunElevated` takes `(IReadOnlyList<string> arguments, TimeSpan timeout)`. Each argument is quoted through `ProcessStartInfo.ArgumentList`, so callers pass elements, never a pre-joined command line. `ElevationUtilities.DefaultElevatedTimeout` is the 60-second default.

Consumer migration for this change: file-wizard `file-wizard/CliServices.cs` (the `TryRunElevated` delegate becomes `Func<IReadOnlyList<string>, TimeSpan, bool>`), `file-wizard/ConfigureDefenderCommand.cs`, `FileWizard/DelegateElevationProvider.cs` and `FileWizard/WindowsDefender.cs` move to the `TryRunElevated(IReadOnlyList<string>, TimeSpan)` shape, and `file-wizard/LargestSummaryCommand.cs` only passes an `IElevationProvider` through. git-wizard `GitWizard/WindowsDefender.cs` moves to the same shape. Neither consumer reads `UsnJournalEntry.Timestamp` in production code; their tests rename the `Timestamp` initializer of `UsnJournalEntryOptions` to `TimestampUtc` and update their fake `IElevationProvider` implementations. The `ElevationUtilities` statics are gone: file-wizard `FileWizardMaui/MainPage.Scanning.cs`, `file-wizard/BrokerSmoke.cs`, `file-wizard/CliServices.cs`, `file-wizard/ConfigureDefenderCommand.cs`, `FileWizardTests/CliServicesTests.cs` and `FileWizardTests/JournalCommandTests.cs`, and git-wizard `GitWizard/Watch/VolumeChangeSourceFactory.cs`, `GitWizardTests/ElevationCoverageTests.cs`, `GitWizardTests/Watch/IndexVolumeChangeSourceWindowsTests.cs` and `GitWizardTests/Watch/VolumeChangeSourceFactoryTests.cs` call the same members on `ElevationUtilities.DefaultProvider` instead (a method group such as `ElevationUtilities.TryRunElevated` becomes `ElevationUtilities.DefaultProvider.TryRunElevated`).

### Added

- `FileIndex.EnumerateRows(SearchQuery, CancellationToken)` yields non-allocating `IndexRow` views with span names, sizes and flags, and `ToEntry()` for rows the caller retains.
- `MftIndexSources.FromLocalVolumes(scanOptions)` supplies an in-process scan for an elevated Windows caller, with no watch source. Concurrent scans share parse threads through the internal allocator ([MFTLib pull request 400 (local-volume index source)](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/pulls/400)).
- `ScriptedDriveWatch.FailApply(Exception)` scripts a batch application failure and automatic recovery ([MFTLib pull request 397 (script application faults)](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/pulls/397)).
- Consumer test data uses `SyntheticJournalRecord`, `SyntheticJournalCursor`, `SyntheticJournalReason`, `SyntheticNotifications` and `SyntheticScanRecord` ([MFTLib pull request 392 (consumer synthetic data)](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/pulls/392)). Migration: file-wizard `FileWizardTests/TestSupport/BrokerProcessFixture.cs` and git-wizard `GitWizardTests/TestSupport/BlockBrokerFixture.cs` construct these records with object initializers and use the synthetic cursor and reason types.
- `MftIndexSources.FromLocalVolumes` stamps the journal cursor before cached direct scans. Reopening adopts only an exactly unmoved journal (or an unavailable query); otherwise it rescans, reporting `JournalAdvanced`, `CheckpointTrimmed` or `JournalRecreated`. Cache-only opens retain an unresumable snapshot and its report. `JournalAdvanced` supplies no retention-size hints. NoCache skips the journal query and stamps zero; cached scans require an active journal. Dump sources remain uncached with a zero cursor.
- `IndexScanPhase.Finished` and `IndexScanProgress.Outcome` (`IndexScanOutcome`: `Succeeded`, `Failed`, `Cancelled`) give `FileIndexOptions.Progress` one terminal sample per drive scan, reported by `FileIndex` after the producer's last sample for MFT-backed and enumeration-backed drives alike, in `OpenAsync` and in rescans. `RowsWritten` is the finished block's row count on success and 0 otherwise. A rescan or a lost-catch-up retry is a scan of its own, so a consumer tracks finished drives as a set ([MFTLib#330](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/330))
- `InProcessBrokerHandle` (`Ended`, `Crash()`, `Scans`) is what `BrokerTestHarness.StartInProcess` returns; `Crash()` closes every host pipe end at once, as a dying broker process does, so the client observes an unexpected end instead of the graceful "disposed" one. `StartInProcess(ScriptedBrokerVolumes)` needs no writer or section factory. `BrokerDiagnosticsIsolation.Reset()` restores default diagnostics state for tests ([MFTLib issue 330 (watch and test support)](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/330))
- `BrokerScanOptions.IncludeFreed` (default false) makes a cold scan of a live volume, direct or through the broker, also import freed MFT records as scan-scoped rows with `FileEntry.IsDeleted` true; a later watch applies journal events to live rows only. A freed row keeps its parent and full path only when every parent through the root is a directory with a trusted sequence (equal, or one higher for a freed parent, within 128 components and without a cycle); any other freed row is detached, so its path is its bare name and it is nobody's child. `SearchQuery.IncludeDeleted` (default false) makes `Search`, `Enumerate` and `EnumerateRows` return deleted rows too; `FileIndex.Find`, `FileIndex.Root` and `FileEntry.Children` return live rows only. The `ArmAndScan` frame gains a 4-byte flag after the profile. A consumer that changes `IncludeFreed` also changes its `CacheTag` version ([MFTLib#292](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/292)).
- `ParseThreadAllowance` supplies a mutable per-scan parse-thread share that native parsing reads at each chunk.
- `JournalCatchUpLostException` reports a journal-proven scan catch-up loss and whether automatic recovery stopped; the drive, consecutive count and `JournalCheckpointLoss` are the drive's `DriveWatchStatus.ConsecutiveLostCatchUps` and `CheckpointLoss`.
- `DriveOperationOutcome` and `DriveOperationResult` support the public token-only all-drive `StartWatchingAsync`, `StopWatchingAsync` and `WaitForCatchUpAsync` calls and the list-form `RescanAsync`; each batched call returns one ordered result per requested drive after all per-drive work settles.
- `MftBlockProduceResult.CatchUpLoss` and `BrokerDriveScanResult.CatchUpLoss` carry a complete but unresumable scan block when the host proves that its armed cursor fell out of the journal.
- `DriveWatchStatus.ConsecutiveLostCatchUps` and `FileIndex.LostCatchUpRecoveryLimit` expose the per-drive recovery count and its limit of three. A scan whose catch-up holds resets the count; at the limit the last block remains queryable but its watch is refused until a consumer rescan.
- `JournalCheckpointLossDetection.ScanCatchUp`, `WatchFaultKind.CatchUpLost`, `WatchFaultKind.Recovery`, and `WatchCatchUpState.Recovering` identify scan-time journal loss and automatic per-drive recovery.
- `BrokerTestHarness.StartInProcess` runs the production broker host in process over in-memory control and drive pipes and returns `InProcessBrokerHandle`.

Drives settle concurrently, callbacks may overlap and arrive out of count order, and a cancelled settle reports nothing. - `DriveWatchStatus.CheckpointLoss` and the `JournalCheckpointLoss` record report, without elevation, that a drive was cold-scanned because its cached block's USN journal checkpoint was absent from the journal: the cause, the journal's `JournalSettings` (`AllocationDelta` and `MaximumSize`) when the loss was detected, how far behind the checkpoint was in bytes, and the size a journal would need to be at least to have kept it. When a drive's watch faults, MFTLib asks the live journal about the position that watch had reached, which is the drive's block cursor and so the same number a warm start asks about; the classification is the journal's answer rather than a reading of the exception. The drive keeps its block and its rows with nothing after the lost position applied, the report is recorded before the `WatchFaulted` event is raised, and a successful `RescanAsync` clears it. No broker frame or native ABI change: the query is unelevated and runs on the client side ([MFTLib#224](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/224))
- `JournalCheckpointLoss.DetectedDuring` and the `JournalCheckpointLossDetection` enum (`DriveOpening`, `LiveWatch`, `ScanCatchUp`) identify the check that found a loss. Reports remain until a newer report replaces them or a consumer rescan clears them; unrelated faults do not rewrite or clear them. `DetectedDuring` is a required init member ([MFTLib#224](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/224))

- `FileEntry.IsDisposed` reports that the handle's snapshot has been released, distinct from `IsValid` (the default struct value) and `IsDeleted` (a tombstoned row); reads of mapped entry data on a disposed handle throw `ObjectDisposedException`, while `IsValid`, `IsDisposed` and the diagnostic `ToString()` remain readable ([MFTLib#145](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/145))
- `MftRecord.SequenceNumber` and `UsnJournalEntry.SequenceNumber` expose the NTFS record's sequence number; combined with the record number as `(sequenceNumber << 48) | recordNumber`, it forms the file reference `FileEntry.Open` uses to detect an MFT record NTFS has reused for a different file
- `DriveBlockStatus.LiveRowCount` reports rows in use and not tombstoned, distinct from the highest-used-slot-plus-one row count the block header keeps
- `MftRecord.Size`, `SizeKnown`, and `ModifiedUtc` expose unnamed data-stream size and modification time from the native parser
- `FileIndexOptions.ProducerPolicy` and `MftSource`, with `ProducerPolicy`, select MFT or enumeration for initial scans and rescans; `MftIndexSource` carries the block producer and the watch source of every MFT-backed drive as one object, and `MftIndexSource.Unavailable(reason)` is the source of a process that cannot scan
- `DriveStatus.FailureMessage` reports the MFT failure; a drive whose MFT producer fails is reported `DriveState.Failed` and never falls back to a directory walk
- `IndexScanPhase` (`Enumerating`, `ParsingMft`, `Transferring`) and `IndexScanProgress` report scan progress uniformly across both producers
- `FileIndex.StartWatchingAsync` and `StopWatchingAsync` start and stop independent MFT-backed drive watches; `FileIndex.Changed` raises one event per applied change and `FileIndex.WatchFaulted` reports every fault with a drive letter and `WatchFaultKind`
- `DriveWatchStatus.FailureMessage` reports a drive's live-watch failure without invalidating its block; it clears when the drive is re-armed or rescanned
- `FileIndex.RescanAsync` retires, rebuilds, and conditionally restarts the named drive's watch while every other drive remains independent
- `FileChange.PreviousPath` carries the full previous path of a rename
- `FileEntry.Open` opens an MFT-producer entry by NTFS file id against a handle on the target volume, which needs no elevation
- `IndexedDrive.FromWindowsVolume` builds a drive from a Windows drive letter, reading its real volume serial so a re-lettered or replaced volume never matches the wrong cached block
- A stale persisted journal cursor is reported as that drive's `Error`, ending only its stream
- Optional trailing `CancellationToken` parameters on every entry point that scans rows: `FileIndex.Find`, `Search`, `Enumerate`, `EnumerateRows` and `Root`, and `FileEntry.Children`. The token is read before the first row and then at least every 4096 rows, so a whole-drive scan can be abandoned promptly; cancellation surfaces as `OperationCanceledException`
- `DriveStatus.FailureKind` and the `DriveFailureKind` enum (`None`, `CacheDeclined`, `ProducerFailed`) say why a `DriveState.Failed` drive has no block: a cache-only open that found no usable cache reports `CacheDeclined`, an MFT producer failure reports `ProducerFailed`, and every other state reads `None`. `FileIndex.RescanAsync` now scans and adopts a blockless failed drive, clearing the kind to `None` on success and re-reporting the drive as `ProducerFailed` when that scan fails; an offline drive still refuses a rescan ([file-wizard#423](https://gitea.fleet.sticktoitive.net/schoen/file-wizard/issues/423))
- `DriveFailureKind.InUse` reports a cache-only open that found the drive's cache block owned by another live `FileIndex`: the second opener never validates, renames, or deletes a block whose per-block owner lock it cannot take, so one index can no longer delete a cache out from under another (the file-wizard#424 incident). A non-cache-only open in the same situation scans into a private delete-on-close block and leaves the canonical cache untouched; once the owner is gone, the next open or rescan takes the slot and warm-starts or replaces the cache as before
- `FileIndexOptions.Diagnostics` receives one line for every block-file delete the index performs (a rejected cache validation, a stale ".retired-*" sweep, a superseded block's final release, a cancelled scan's partial replacement, or a rejected producer block), with the deleted path and the reason; `BlockFileCreateOptions.Diagnostics` forwards the same hook through block creation. Null by default, which logs nothing.
- `DriveWatchStatus.Requested` reports whether a drive's watch is requested, which is what decides whether a rescan restarts it. A start whose source threw or that was refused over an unresumable block leaves it set; stop clears it ([MFTLib#330](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/330)).
- `FileIndex.WatchStateChanged` raises a `DriveWatchState` (`DriveLetter`, `CatchUpState`, `StateVersion`, `Fault`) for every change of a drive's `DriveWatchStatus.CatchUpState`, and `DriveWatchStatus.StateVersion` carries the same per-drive version, so a consumer observes an automatic recovery finishing (`Recovering`, then `CatchingUp`, then `CaughtUp`) without polling, and orders its own readiness against a fault that lands after it read the drive: a decision tagged with version v is superseded by any later event of that drive. Each change is delivered once, with neither the state lock nor a write gate held, one drive's changes in version order, before the `WatchFaulted` of the fault that caused it; disposal delivers each drive's final change before `DisposeAsync` returns. A consumer that also reads `Drives` applies only versions newer than the last it applied ([MFTLib#330](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/330)).

  - `ReadUsnJournal(cursor)` - batch catch-up read; returns `(UsnJournalEntry[] Entries, UsnJournalCursor UpdatedCursor)`. Throws `InvalidOperationException` if the journal was recreated or entries were overwritten (caller should fall back to a full rescan)
  - `WatchUsnJournal(cursor, cancellationToken)` - live `(UsnJournalEntry[] Entries, UsnJournalCursor Cursor)` batches; blocks on the kernel (zero CPU) until changes arrive, unblocks via `CancelIoEx` on cancellation, and supplies the post-batch cursor for persistence

  - `MftResult.MaterializeBatches(int batchSize = 4096)` - yields materialized batches of records with bounded memory footprint over the existing result lifetime
  - Unified `ToArray()` row decoding over `MaterializeBatches()` while maintaining full source compatibility
- **VolumeBroker subsystem** - `BrokerSession` owns one elevated process and control pipe, and the process runs one scan or watch on each drive pipe. `BrokerScanOptions` configures a scan, `NtfsVolumeInformation` reports a volume's geometry, and `BrokerDiagnostics` traces tagged channels through a bounded background writer. `ElevatedEntryPoint.TryHandle` dispatches `--broker --pipe NAME`, and `BrokerLauncher.Launch` starts the child through `runas`.

### Changed

Signature changes are written as `before -> after`. Baselines: `0.2.0` is the last published release (tag `v0.2.0`); "0.3.0 preview" is the API just before the per-drive watch channels change ([MFTLib#265](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/265), commit `3597586`), which file-wizard and git-wizard built against.

- `BrokerProcess` and `BrokerChannelLostException` are internal, as is `InProcessBrokerHandle.Process`. Consumer tests observe `Ended`, simulate death with `Crash()` and inspect `Scans`; sessions take the handle through `BrokerTestHarness.CreateSession(launchAsync)`.
- `BrokerTestHarness.StartInProcess(...)` returns `InProcessBrokerHandle`; sessions and tests read its `Ended`, `Crash()` and `Scans`.
- The broker end notification is the `Task<string> Ended` of `BrokerSession` for applications and of `InProcessBrokerHandle` for tests. The task completes once with the end reason, including for callers that look after the end, and never faults. Read `Ended.IsCompleted` for a poll, and continue on `Ended` where a handler would be subscribed.
- `BrokerDiagnostics.Log(string message)` -> `BrokerDiagnosticsIsolation.Log(string channel, string message)`. Records are queued to one bounded background writer, so diagnostics I/O never blocks a broker operation.
- `MftVolume.StreamRecords(string? filter = null, MatchFlags matchFlags = MatchFlags.None)` (0.2.0) -> `StreamRecords(bool includeFreed, IProgress<MftScanProgress>? progress, ParseThreadAllowance? parseThreads, CancellationToken cancellationToken)`. No parameter has a default, and the parse filters no names and resolves no paths.
- `FileIndex.StartWatchingAsync(CancellationToken)`, `StopWatchingAsync(CancellationToken)`, and `WaitForCatchUpAsync(CancellationToken)`: `Task` -> `Task<IReadOnlyList<DriveOperationResult>>`, one ordered result per drive. The only public `IReadOnlyList<char>` overload is `RescanAsync(IReadOnlyList<char>, CancellationToken)`, which returns one ordered result per listed drive; the public single-drive `StartWatchingAsync`, `WaitForCatchUpAsync` and `RescanAsync` `(char driveLetter, CancellationToken)` overloads keep returning `Task`, and single-drive `StopWatchingAsync` is internal.
- `WatchFault(WatchFaultKind Kind, char? DriveLetter, Exception Exception)` -> `WatchFault(WatchFaultKind Kind, char DriveLetter, Exception Exception)`. `WatchFaultKind.Source` is replaced by `Drive`, `Channel`, `CatchUpLost`, `Recovery`, and `RescanRestart`.
- `IndexDriveOpened.Ordinal` -> `IndexDriveOpened.SettledCount` (1-based settle order).
- `IndexScanPhase` { `Enumerating`, `ParsingMft`, `Transferring` } -> adds `Finished`, and `IndexScanProgress` gains the nullable `Outcome` (`IndexScanOutcome`). `FileIndex` reports one `Finished` per drive scan; a consumer that counted a drive finished on its first `Transferring` sample (or on a drive change) should count it on `Finished` instead, and switches over `IndexScanPhase` handle the new member.
- `MftVolume.StreamRecords(bool includeFreed, IProgress<MftScanProgress>? progress, ParseThreadAllowance? parseThreads, CancellationToken cancellationToken)` exposes parse-thread allowance, progress, and cancellation. Cancellation reaches the native parser between chunks and between 4096-record worker slices; the native ABI is version 7 and carries cancellation state plus the current thread allowance.
- `BrokerSession.CreateIndexSource` supplies the broker-backed block producer and the per-drive watch source together, both connected through the session's one launch.
- `FileIndex` watch lifecycle is per drive. Public single-drive start, rescan and catch-up waits affect only the named drive; list-form rescan and token-only all-drive start, stop and catch-up waits run drives concurrently. `Drive` and `Apply` faults publish `Recovering` and trigger one automatic rescan, `Channel` faults do not recover, and a failed recovery raises `WatchFaultKind.Recovery` and leaves the drive faulted for a consumer start or rescan.
- `WatchFault.DriveLetter` is a non-nullable `char`; `WatchFaultKind` is ordered as `Subscriber`, `Drive`, `Apply`, `CatchUpLost`, `Channel`, `Recovery`. `WatchCatchUpState.Recovering` sits between `CaughtUp` and `Faulted`.
- `FileIndex.OpenAsync` settles configured drives concurrently. `IndexDriveOpened.SettledCount` is the 1-based settle order; progress callbacks run on each settling thread, may overlap, and may arrive out of count order. A cancelled drive settle reports nothing, so a failed or cancelled open can report only a subset.
- `BrokerProtocol` and `BrokerFrame` use request ids on control frames and drive-scoped payloads on operation channels. The drive channel supplies drive scope; its `ArmAndScan`, `StartWatch`, `JournalBatch`, `CaughtUp`, and `Error` frames contain neither a drive nor an arm generation. Scan catch-up loss is terminal and explicit.
- `FileIndex.StartWatchingAsync(X)` completes after X's channel is connected, `StartWatch` is written, and the ready handle is published with its pump queued. Readiness is per drive and separate from `WaitForCatchUpAsync` ([MFTLib#247](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/247))
- A cache-mode `FileIndex` now holds a sibling `<block>.lock` file (opened with `FileShare.None`) for as long as it owns a canonical cache block. A second `FileIndex` over the same cache directory - in any process - that cannot take that lock reports the drive `Failed` with `DriveFailureKind.InUse` on a cache-only open instead of warm-starting or deleting the block. Consumers that deliberately shared one cache block between two live indexes must open the second index with `NoCache` or expect the in-use outcome
- **Recompile required.** The optional `CancellationToken` parameters listed above are source compatible but not binary compatible: a consumer bound to the 0.3.0 assemblies calls method signatures that no longer exist and fails at runtime with `MissingMethodException` until it is rebuilt against this version. This matters for a consumer that vendors prebuilt MFTLib binaries rather than building from source
- `FileChange` gains a required positional `Timestamp` parameter between `Path` and `PreviousPath`. Consumers that only receive `FileChange` instances (the `Changed` event, `ApplyJournalEntries`) need no source change; any code that constructs a `FileChange` must pass the originating record's timestamp and, like the rest of this release, recompile against this version
- Scanning on one thread while another disposes the index is safe. Each of the six entry points above holds the snapshot it reads for its whole duration, and `FileIndex.DisposeAsync` cancels the queries in flight and waits for every one of those readers to leave, on the current snapshot and on the retired ones, before it unmaps anything. A query racing disposal ends with `OperationCanceledException`, or `ObjectDisposedException` if it had not started, rather than reading a released mapping. `FileEntry.Children` carries no reference to its index, so disposal waits that listing out rather than cancelling it. Every other `FileEntry` member reads a single row and keeps its per-access `IsDisposed` check, which is unchanged

- `FileIndex.Find` accepts a native filesystem path and resolves it against the longest matching indexed root directory instead of requiring a `X:\` drive-letter prefix, so it is the exact inverse of `FileEntry.Path` on every platform, including a Linux file name containing a backslash. Child names match by the block's own rule: an MFT block folds case, an enumeration block over a case-sensitive root matches ordinally ([MFTLib#143](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/143))
- `FileEntry.Path` renders the drive block's real root directory joined with the name chain using the host separator, so it is openable and can be looked up again on any platform; the drive key is never rendered into a path. `FileChange.Path` and `PreviousPath` come from the same builder and change with it. A Windows MFT block is byte-identical because its root directory is `X:\` ([MFTLib#143](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/143))
- `FileIndex.DisposeAsync` releases every snapshot it holds, current and retired, unconditionally, including retired snapshots whose handles are already unreachable. It returns only once those blocks are actually closed: a release a snapshot finalizer has already begun is waited out rather than taken for a finished one. During an index's lifetime, a retired snapshot still releases through its finalizer once handles minted before the rescan are unreachable. A `FileEntry` held across disposal reports `IsDisposed` and throws `ObjectDisposedException` on reads of mapped entry data; `IsValid`, `IsDisposed` and the diagnostic `ToString()` remain readable ([MFTLib#145](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/145))
- The native interface version constant (`MFT_NATIVE_ABI_VERSION`) is 7; compact entries are 52 bytes (the last field is the sequence the record's name stores in its parent reference), `MftParseResult` includes cancellation state for the parse control block and an invalid-input flag for a rejected file, and its message buffer is UTF-16 on every platform. Managed and native binaries must match
- Block format version is 3: the declared header is 112 bytes (`LiveRowCount` at offset 88, `SequenceRegionOffset` at offset 96, `CacheTagFourCc` at offset 104, and `CacheTagVersion` at offset 108), and a sequence-number region sits between the row region and the name pool. A version mismatch means discard the block and rescan
- `FileIndexOptions.NoCache` blocks are created with `FileOptions.DeleteOnClose`, so the operating system removes them when the last handle closes, including on a killed process, instead of relying on a managed delete during dispose plus a stale-block sweep on the next open
- `ScanReady` carries `SkippedRecordCount` (one int64 field)
- `BlockScanOutcome` carries `Block` and `SkippedRecordCount`; the caller owns the block
- `StartWatchingAsync` refused over an unresumable journal cursor (a cache-only adoption past a lost checkpoint, or lost catch-ups at `LostCatchUpRecoveryLimit`) now records the watch request, as a source failure always did: the `RescanAsync` the refusal asks for restarts the watch, and `StopWatchingAsync` on the refused drive withdraws the request instead of throwing. A drive whose watch was never requested is still never started by a rescan ([MFTLib#330](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/330)). Consumer migration: file-wizard `FileWizardMaui/MainPage.DriveRescan.cs` (`StartRescannedDriveWatchAsync`) keys on `Watch.Supported && !Watch.Requested` instead of `WatchCatchUp == NotStarted` and drops the refused-drive half of its comment; file-wizard `FileWizard/JournalWatcher.cs` corrects its comment that `NotStarted` covers a refused start.

- MFT file record geometry is now detected at runtime instead of assumed to be 1024 bytes: native volume parsing queries the volume's actual record size (`FSCTL_GET_NTFS_VOLUME_DATA`) at parse time, and parsing an exported MFT file reads the record size out of record 0's header. Both 1024-byte and 4096-byte record sizes are supported
- Versioned Compact Native ABI (version 2): compact entries carry size, modification time, and sequence number, while the parse result reports cancellation
- Added native and managed ABI compatibility checks via `GetMftNativeAbiVersion()` and `EnsureCompatibleNativeAbi()`
- Self-elevation now returns `false` without attempting UAC when no interactive desktop is available (for example, CI or a Session 0 service)
- Reorganized managed sources by MFT, journal, broker, elevation, interop, and internal responsibilities; split scan, journal, broker connection, transport, and session behavior into focused partials without changing the public API
- Reworked the README and added a broker integration guide covering installation, API selection, memory lifetime, race-free scan/catch-up, live watch, rescans, recovery, and deployment
- Fixed native `bool` marshaling for synthetic generation so conversion failures reliably propagate to managed callers
- Fixed synthetic generator teardown after an asynchronous write failure so the completed writer is joined exactly once
- A `BrokerSession` connection has a bounded timeout (default 30 seconds) and throws a descriptive `TimeoutException` if the elevated child does not connect to the control pipe
- The root directory record (MFT record 5) survives a scan: its `FileName` reads `.`, so `StreamRecords` results and broker-written blocks keep the record and journal entries created directly under the root resolve their parent
- `scripts/build-windows.ps1` owns the Windows native and managed build recipe (NuGet restore, amd64 MSBuild of `MFTLibNative.vcxproj`, then the managed builds) for `init.ps1`, `scripts/run-coverage.ps1` and CI, replacing three drifted copies; `scripts/build-windows.tests.ps1` pins its tool discovery, argument generation and error propagation and runs in the `windows` CI job ([MFTLib#381](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/381))
- The post-clean init verification in `.gitea/workflows/test.yml` (`git clean -ffxd`, both init entry points, `init.ps1 -Build`, with a clean-tree check after each) runs on pushes to `main` only, not on pull requests, and the host-mode Windows jobs of `test.yml` and `aislop.yml` no longer use `actions/setup-dotnet` (the host provides the .NET SDK); the Linux jobs take it from the fleet runner image and use no `actions/setup-dotnet` either ([MFTLib#380](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/380))

### Fixed

- `FileIndex.StartWatchingAsync` honors cancellation while the broker-backed watch source opens the drive channel and writes `StartWatch`; cancellation closes that operation's pipe before the start throws ([MFTLib#250](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/250))
- Broker watch startup errors add cached-cursor rescan guidance only when a live journal query confirms a changed journal id or a checkpoint older than `FirstUsn`. Unrelated messages containing words such as "cursor" or "deleted" no longer trigger that guidance, and lost-cursor guidance no longer depends on native error wording. If the journal cannot answer, the original error is preserved. Broker frames and the native ABI are unchanged.
- Broker diagnostics no longer feed the watch they observe: while diagnostics are enabled, the broker drops journal entries for both `broker-diagnostics.log` files (its own and the client's, forwarded across the runas boundary as `--diag-log`) before building JournalBatch frames, and skips batches the filter empties, so a live watch with diagnostics on no longer generates self-sustaining journal traffic; `MFTLIB_BROKER_DIAG_INCLUDE_SELF=1` opts back in ([file-wizard#299](https://gitea.fleet.sticktoitive.net/schoen/file-wizard/issues/299), [git-wizard#143](https://gitea.fleet.sticktoitive.net/schoen/git-wizard/issues/143))

- A `BlockWriter` write racing `BlockFile.Dispose` on another thread (a broker test fixture tearing down while its serving task is mid-row-write) could dereference an unmapped view and kill the process with an `AccessViolationException`; disposal now refuses new writer operations when it begins and waits for in-flight ones before unmapping, so a late writer fails with a catchable `ObjectDisposedException` (refiled from [git-wizard#181](https://gitea.fleet.sticktoitive.net/schoen/git-wizard/issues/181))
- A fault on one drive is scoped to that drive's watch instance and cannot end, delay, or mutate a sibling drive's watch.
- A journal-invalidation `Error` frame ends only its drive channel with a drive watch fault; sibling channels keep streaming.
- `IndexNavigation.BuildPath`, `IsUnder`, and subtree-restricted queries explicitly throw `InvalidDataException` when a valid parent chain exceeds `BlockLayout.MaximumPathDepth` hops instead of silently returning truncated paths or false negatives, while preserving cycle detection
- Under capacity exhaustion (such as a delete following an unrecorded create), `JournalMutator` suppresses the `FileChangeKind.Deleted` change event when row hydration fails rather than emitting an invalid event for an unrecorded record
- `Microsoft.SourceLink.GitHub` bumped from 8.0.0 to 10.0.401, moving the transitively pulled `Microsoft.Build.Tasks.Git` past the version affected by CVE-2026-62900 ([GHSA-23fw-v26w-5fgq](https://github.com/advisories/GHSA-23fw-v26w-5fgq))
- An aggregate `FileIndex.WaitForCatchUpAsync(CancellationToken)` that ended by cancellation or fault stayed reachable from every drive still catching up, through a slot-completion continuation that could never be detached, so repeated bounded waits against a drive that never caught up accumulated one wait coordinator each; the continuations are now cancelled, which removes them from the pending drive, as soon as the aggregate wait completes, cancels, or faults ([MFTLib#182](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/182))
- Closing a drive pipe cancels only that drive operation; closing the control pipe ends the host session and every channel without an unhandled broken-pipe exception ([MFTLib#196](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/196), [MFTLib#199](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/199))
- Per-drive watch channels close the cross-drive head-of-line blocking and fault-coupling tracked by [MFTLib#252](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/252).
- `WaitForCatchUpAsync` faulted when a drive's watch failed before the drive read `Recovering` and before its `LiveWatch` checkpoint loss was recorded, so a consumer reading `Drives` from the wait's fault path saw `Faulted`. The wait now faults after both are recorded, just before `WatchFaulted` is raised ([MFTLib#330](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/330)).
- During a rescan of a drive whose watch is requested, between the commit that retires the old watch and the replacement registering, the drive read `NotStarted` and `WaitForCatchUpAsync` threw "is not being watched". It now reads `CatchingUp`, and a wait issued then follows the replacement watch, faulting if the replacement cannot start or the scan's catch-up is lost ([MFTLib#330](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/330)).
- The `WatchCatchUpState` and `DriveWatchStatus.CatchUpState` documentation said a drive with no current watch reads `NotStarted`; a drive whose start or automatic recovery failed reads `Faulted`, which is what the code has always done ([MFTLib#330](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/issues/330)).
- `JournalMutator` treats a data write inside the create cycle as part of the creation, so a create-write-close followed by one append reports `Created` plus one `Modified` ([MFTLib#310](https://gitea.fleet.sticktoitive.net/schoen/MFTLib/pulls/310)).
